# Goal-Directed Research Loop on Cloudflare

A durable, self-continuing **research agent** on Cloudflare.

> **Plan & cost, measured — read before running:**
>
> - **HTML ingest does not fit the Free plan.** A 211 KB page costs **229–644 ms CPU**
>   against a 10 ms per-step limit; even a 12 KB page costs 15 ms. ([§4.2](#42-the-cpu-problem--measured-and-it-does-not-fit-the-free-plan))
> - **Plain text and markdown cost ~1 ms regardless of size**, so the Free plan *is*
>   viable at **~58 iterations/day** if you seed only `llms.txt`, `index.md`, RSS and
>   JSON sources. ([§4.3](#43-what-actually-fits-in-the-free-plan-per-day))
> - **Free can never bill you** — limits fail with errors. **Paid auto-bills overages,
>   and Cloudflare's budget alerts do not cap anything.** This build ships its own hard
>   stop, `DAILY_NEURON_BUDGET`, set **below** the free allocation because the
>   allocation is not enforced on a UTC calendar day. ([§4.4](#44-billing-what-happens-past-the-free-quota))
> - **The spend guard was wrong three times** (bugs.md #17, #19, #21) and each fix
>   passed its own test. Only reconciling against Cloudflare's own analytics found the
>   truth. If you fork this, run that reconciliation before trusting the meter.

You submit a topic, a set of goals, and seed source URLs. The loop then repeatedly:
fetches a source → ingests it into vector memory → recalls what's relevant →
reasons over it → records a finding → self-assesses against the goals.
It stops when the goals are met, the sources are exhausted, or an iteration cap is hit.

Vector memory is what makes this a research loop rather than a chatbot in a `for` loop:
it lets iteration 40 recall what iteration 3 read, without carrying 40 iterations of
text in the context window.

**Stack:** Workers + Workflows + Workers AI + Vectorize + D1.

## 1. Findings

### 1.1 "Cloudflare Computer" is real, but it is not what you think

This project began from notes (generated by another LLM) describing "Cloudflare Computer"
as a unified umbrella brand fusing Workers, D1, R2, Vectorize, Workers AI, Queues and
containers into one product.

**That description is wrong.**

[`@cloudflare/computer`](https://blog.cloudflare.com/cloudflare-computer/) shipped on
**2026-08-03** ([changelog](https://developers.cloudflare.com/changelog/post/2026-08-03-cloudflare-computer/))
as an early-preview **agent runtime library**. It gives an agent its own *computer*:

- A virtual filesystem backed by Durable Object SQLite
- Shell execution (`exec`), file read/write/edit/ls, git operations
- Automatic orchestration between fast isolates and full Linux containers
- An AI SDK-compatible toolkit

```js
import { Workspace } from "@cloudflare/computer";
const workspace = new Workspace({ storage: this.ctx.storage, useThink: true });
```

It is explicitly **not production-ready**, and it is the agent's *hands*, not its memory
or its loop. It does not replace Workers, and it has no bearing on this build.

**Road not taken:** [`@cloudflare/think`](https://developers.cloudflare.com/agents/harnesses/think/)
is the companion agent-loop framework — an opinionated base class handling the agentic
loop, message persistence, streaming and tools over Durable Object SQLite. It's a strong
fit for a *conversational* agent. We didn't use it because this is a headless, scheduled,
long-horizon research loop where Workflows' durable execution and step-level retries
matter more than chat plumbing.

### 1.2 Fabricated APIs in the source notes

Every row below was in the original notes. None of it compiles.

| Claim in the notes | Reality |
|---|---|
| `step.call("self")` for infinite recursion | **Does not exist** on `WorkflowStep`. There is no self-call API. |
| A Workflow can loop forever in one instance | **No.** Free plan caps at **1,024 steps per instance**. Requires a trampoline. |
| `import { Ai } from '@cloudflare/ai'`; `new Ai(env.AI)` | Deprecated package. It's now just `env.AI.run(model, opts)`. |
| `env.WORKFLOWS.trigger("loop")` | Not an API. Instances are created with `env.BINDING.create({ id, params })`. |
| `env.STATE.get/put(...)` | A KV binding that was never declared in their config. |
| "Cloudflare Computer" as an umbrella product | See §1.1. |
| "AI inference free for many models" | Actually a single shared budget: **10,000 Neurons/day**. |

### 1.3 Things only discovered by running it

These cost real debugging time and are not obvious from the docs.

**Workers AI returns `response` as a string OR an object.** For prose it's a
string. When the model emits valid JSON — which this prompt explicitly asks for —
the binding *auto-parses it* and `response` is an object. Calling `.trim()` on it
throws `TypeError: raw.trim is not a function`. `parseReasoning()` handles both.

**`usage.neurons` is returned on *text generation* calls — and NOT on embeddings.**
This sentence used to say "on every call", and that error is what made the spend
guard read every embedding as free (bugs.md #21):

```jsonc
// @cf/meta/llama-3.3-70b-instruct-fp8-fast
"usage": { "prompt_tokens": 42, "completion_tokens": 2, "neurons": 1.5296 }

// @cf/baai/bge-small-en-v1.5 — note what is missing
"usage": { "prompt_tokens": 9, "completion_tokens": 0, "total_tokens": 9 }
```

Use `usage.neurons` where it exists; price embeddings from `total_tokens` times the
model's published rate (1,841 neurons/M input tokens for `bge-small-en-v1.5`).
**Never default a missing cost to `0`** — that turns *unknown* into *free*, which is
the worst possible failure direction for a spend guard. `priceCall()` in `db.ts`
logs an error for any model it cannot price.

**Vectorize inserts are asynchronous — measured 15–30s to become queryable.**
A `query()` issued in the same iteration as the matching `upsert()` returns
**zero matches**. This silently makes vector memory look broken. The loop
therefore carries the current source's text directly into the prompt
(`IngestResult.excerpts`) and uses Vectorize only for *earlier* sources. Never
let an iteration depend on recalling what it just wrote.

**Vector IDs keyed on the iteration number silently destroy data.** The original
key was `${runId}:${type}:${n}:${i}`. A failed iteration doesn't advance
`iterations`, so the next attempt reuses `n` — and `upsert` overwrote the
previous source's vectors. Symptom: chunk counts look right in D1, but search
only ever returns the most recent source. Chunks are now keyed by **source id**
(`chunkKey`), findings by iteration (`findingKey`).

**`Number(v) || fallback` discards a legitimate `0`.** `MAX_SOURCE_DEPTH="0"` is
documented as "seeds only", but `Number("0") || 2` evaluates to `2`, so the loop
kept crawling model-proposed URLs. All numeric config now goes through `num()`
in `src/types.ts`, which only falls back on non-finite values.

**Nav boilerplate survives element removal.** Language switchers and category
menus live in bare `<li>`/`<p>` outside any `<nav>`, so `DROP_SELECTOR` misses
them. On one Cloudflare blog post the first chunk was entirely a language menu.
The `denoise()` line filter cut 22,164 chars → 8,699 and 18 chunks → 7, a 61%
reduction in vectors stored and embedding cost, with no loss of article text.

**A failed `LOOP.create()` leaves a zombie run.** The D1 row is written before
the workflow starts (the first step needs its sources). If instance creation then
fails, the row sits at `status='running'` with queued sources, and the watchdog
resurrects it hours later as a run nobody started. `/start` now fails it closed.

### 1.4 Other things worth knowing

- `env.AI.autorag()` is **deprecated**; AI Search now uses the `ai_search_namespaces`
  binding, which can create search instances at runtime.
  ([docs](https://developers.cloudflare.com/ai-search/usage/workers-binding/))
- [AI Gateway Web Search](https://developers.cloudflare.com/ai-gateway/usage/web-search/)
  exists and works as a model tool, but has **no free tier** — it bills at upstream
  provider rates and requires a paid third-party model (Claude, GPT, Perplexity).
  This is why this project uses seeded `fetch()` instead.
- Embedding model IDs use the **vendor path**: `@cf/baai/bge-small-en-v1.5`, not
  `@cf/bge-small-en-v1.5`.

## 2. Design

```
POST /start {topic, goals[], sources[], maxIterations}
   └─> env.LOOP.create({ id: `run-<id>-gen-0`, params })
         │
   ResearchLoop (WorkflowEntrypoint)
     repeat until terminal:
       step.do  "next-source" → D1: claim next pending source (or null)
       step.do  "ingest"      → fetch + HTMLRewriter + chunk
                                → embed → Vectorize.insert(ns=runId, meta{type:"chunk"})
       step.do  "recall"      → embed(goals + open questions)
                                → Vectorize.query(ns=runId, topK=8)
       step.do  "reason"      → env.AI.run(llama, topic+goals+recalled+prior findings)
                                → {finding, progress, newSources[], done}
       step.do  "record"      → D1 finding + Vectorize.insert(meta{type:"finding"})
                                → enqueue newSources
       step.do  "assess"      → done | no sources | n>=maxIterations | stop flag?
       step.sleep INTERVAL                    ← free, does not count toward step cap
     step.do "report"   → final synthesis into D1
     step.do "continue" → if n < maxIterations: create next generation

Cron */30    watchdog: restart a run that died mid-flight
GET  /state?run=       run status, findings, source queue
GET  /search?run=&q=   semantic search over that run's memory
POST /stop?run=        sets D1 stop flag; loop exits at next assess
```

### 2.1 Why a trampoline

A Workflow instance cannot run forever — the free plan allows **1,024 steps**. At 6 steps
per iteration that's ~150 iterations per instance. So each instance runs one *generation*,
then creates the next and exits.

`step.do("continue")` can retry *after* a successful `create()`, which would fork the run.
Deterministic instance IDs make re-entry a no-op:

```ts
try {
  await this.env.LOOP.create({ id: `run-${runId}-gen-${n + 1}`, params });
} catch (e) {
  if (!/already exists/i.test(String(e))) throw e;   // already created — fine
}
```

### 2.2 Why `step.sleep` is the key to pacing

`step.sleep` and `step.sleepUntil` **do not count toward the step limit**
([docs](https://developers.cloudflare.com/workflows/build/workers-api/)). This is what
makes a slow, long-horizon loop viable: the loop can idle for 18 minutes between
iterations to stay inside the daily neuron budget without consuming any step quota.

### 2.3 State must be rebuilt from step returns only

Instances **hibernate** across `step.sleep`. In-memory locals do not survive. Every
carry-forward value (`n`, `prevFindingId`, `openQuestions`) must come back out of a
`step.do` return value — serializable, ≤1 MiB.

This is the single most common way to write a Workflow that passes local testing and
then silently corrupts itself in production.

### 2.4 Why namespaces, not metadata, isolate runs

Vectorize metadata indexes carry an ordering trap, quoted directly from the docs:

> *"Vectors upserted before a metadata index was created won't have their metadata
> contained in that index."*

If you insert first and add the metadata index later, those vectors are **permanently
invisible** to that filter. There is no backfill.

So:
- **`run_id` → namespace.** Namespaces apply *before* filtering, need no pre-declaration,
  and allow 1,000 per index at 64 bytes each. Safe to create at any time.
- **`type` (`chunk` | `finding`) → the one metadata index**, created at setup time,
  **before the first insert ever happens.**

### 2.5 Why the prompt gets fresh text AND recalled memory

Vectorize insert latency (~15–30s, §1.3) means an iteration cannot recall what it
just ingested. So the prompt has two distinct context blocks:

- **`NEW MATERIAL FROM THAT SOURCE`** — `IngestResult.excerpts`, carried directly
  in the step return. Always present, never subject to indexing lag.
- **`RECALLED FROM EARLIER SOURCES`** — Vectorize matches, which cover everything
  read in prior iterations.

Observed working: iteration 1 produced a correct, grounded finding with
`recalled=0`; iteration 2 had `recalled=8` and correctly reported that one goal
was "already met from prior findings".

### 2.6 Why `assess` is a separate step

Termination logic must observe the *committed* results of `record`. Folding the check
into `reason` would let a step retry re-evaluate termination against uncommitted state,
producing a loop that stops early or refuses to stop at all.

### 2.7 Why one source per iteration

Three reasons converge on it: it keeps CPU per invocation low (§4.2), it stays far under
the 50-subrequest cap, and it makes each iteration a clean unit of work that can be
retried independently — which is the entire point of using Workflows.

### 2.8 Why there is a ledger as well as a vector index

The loop answers *"what changed today"*, against a baseline that Claude Code writes
monthly (`benchmark/AU-BRIEF-DECISION.md`). That needs two different kinds of memory and
they are not interchangeable:

| | question it answers | instrument |
|---|---|---|
| Vectorize | "what earlier material is *related* to this?" | similarity, top-K, per-run namespace |
| `events` table | "have I *already reported* this?" | `UNIQUE(key)`, exact, across all runs |

Change detection is an **identity** question, so it gets a UNIQUE constraint rather than
a nearest-neighbour search. A similarity index cannot answer it: two reports of the same
round score high against each other, and so do two different rounds by the same investor.
The ledger is also the only state that crosses days — Vectorize namespaces are per run,
so without it every run starts amnesiac.

The model emits events as pipe-delimited **lines**, not nested JSON:

```
Sophiie AI | construction | $5m | Seed | Blackbird | 2026-08-17 | [S1]
```

`parseReasoning` exists because this model wraps JSON in prose and code fences; asking it
for an array of objects raises the failure rate of the step that produces all the value.
A malformed line is dropped and its neighbours survive, which nested JSON cannot offer.
The trailing `[S1]` is resolved against the iteration's citable set (§ bugs.md #25), so a
ledger row can no more carry an invented URL than a citation can.

**Silence is a valid result.** An iteration that finds nothing new returns `"events": []`
and a one-line finding saying so. Before this, the loop had to produce a finding every
iteration and satisfied that demand by restating recalled material — which is precisely
the pressure that produced #25.

### 2.9 The baseline is data, and the report must not fake it

`control.baseline` holds a document Claude Code writes monthly and the Worker never
generates — the tier split of `benchmark/AU-BRIEF-DECISION.md`. It is rendered into every
iteration prompt under `BASELINE:`, and posted with `POST /baseline {text}`. **Content
needs no deploy; the prompt block did, and shipped.**

For six weeks it was the empty string, and the report said:

```
## Divergence from baseline
None.
```

*Checked and clean*, when the truth was *nothing to check against*. That is the §10
failure — "not measured" and "clean" collapsing onto one word — moved out of the spend
guard and into the deliverable, where it is worse, because the report is the product.

So the **code** owns that section whenever the baseline is absent: it writes
`Not measured — no baseline recorded.`, `NO_BASELINE_RULE` asks the model to omit its
own, and `dropSection()` removes it if the model emits one regardless. The third step is
not redundant. Instruction lost to this model on this exact surface twice (#25, #28) —
on #28 it re-offered an event it had just been shown under `ALREADY RECORDED`. **An
invariant enforced by asking is not enforced.**

The baseline itself (`baseline/AU-AI-FUNDING-2026H1.md`) is written to be diverged from,
which imposes three rules a prose summary would not have:

- **State shares, not only dollars.** Quarters differ in size, so a sector can grow its
  dollars and lose its share. AI models & data infrastructure went $100M → $730M
  Q1→Q2 2026, which is 5.6% → 42.6% *of the quarter* — the second pair is the one a
  daily event can contradict.
- **Label every constructed number as constructed.** Cut Through publishes medians, not
  ranges, so the ⅓×–3× round-size bounds are a stated choice; Q4 2025 is CY2025 minus
  three quarters and carries ±$400M because three different CY2025 totals circulate.
  Unlabelled, a subtraction reads as a measurement within a month.
- **Write "NOT MEASURED" where there is no source, and say what not to flag.** No one
  ranks Australian investors by deal count, so B2 is empty and the baseline instructs the
  loop not to flag investor divergence. Filling it from aggregator pages would have
  reproduced the bug above one section over.

The coverage limits are in the document for the same reason: Q1 2026's sector list is a
**top ten** summing to $1.63B of a stated $1.8B, so "not listed" means *below $76M*, not
zero — and a baseline that did not say so would manufacture divergences every week.

### 2.10 Who owns each section of the report

The report has three sections and the model writes one of them. That split was not a
design choice made up front; each section moved into code after the model got it wrong
in production.

| section | written by | why |
|---|---|---|
| `## New events` | code, from `eventsForRun()` | only the `UNIQUE(key)` insert knows what was actually novel. The model re-offered an event it had just been shown as recorded (#28) |
| `## Round size vs baseline (B3)` | code, from the baseline's own flag table | arithmetic against a fixed table. The model called a $20M Seed "within the expected range" when B3 flags Seed above $12.0M, and checked a stageless round as a Seed when B3 says in words that it cannot be checked — both cited to B3 (#36) |
| `## Divergence from baseline` | the model | sectors only. Round size is answered above it, and B2 instructs the loop not to flag investors at all |
| ~~`## Notes`~~ | **deleted** | every one ever written restated an already-recorded event (#37) |

**The B3 bounds are parsed from the baseline, not copied into code.** They are
constructed — the document states them as ⅓× to 3× the Q2 median — so they are recomputed
on every monthly refresh, and a second copy in TypeScript would drift silently against the
document readers are told is authoritative. The parser anchors on the `flag below / flag
above` header cells, because B3 has a second table with the same column count directly
above it, and the tests read the **real** baseline file so a refresh that breaks the format
fails `npm test` rather than the next daily run.

Every non-verdict is a named result — `stage not stated`, `not a B3 row`, and `NOT CHECKED`
when the table cannot be read — never a blank line that could pass for "nothing breached".
That is §10 on the deliverable, and it is the same failure the empty baseline produced one
section over.

**Why `## Notes` was deleted rather than fixed.** Three were ever written under the delta
brief and all three restated a recorded event. One report printed:

```
## New events
None today.
...
## Notes
Nybro's Seed round has been doubled to $20 million, supported by QIC...
```

A report contradicting itself in 280 characters, in the only section with no source behind
it. The three older, pre-ledger runs never produced one at all, so nothing observed was
lost by removing it.

**The leak upstream is counted, not corrected.** The report only repeated what the finding
wrote, and the prompt forbids naming a recorded event at all — restating one puts it back
into that run's vector namespace for later iterations to recall. But the offending sentence
can carry a genuinely new event alongside the leaked one, so dropping the finding loses real
work and editing prose mid-sentence risks mangling it. Designing that fix from three
anecdotes is what §12 warns against, so `leakedCompanies()` measures it instead, on both
writers — the workflow and `/step` (#24).

It is **50%**: 4 of the 8 findings ever handed a non-empty `ALREADY RECORDED` list named
something on it, across four runs on three days. Stored in `findings.leaked`, NULL when
clean, and the historical rows were backfilled — without that, NULL would mean both "clean"
and "never measured", which is #21 exactly.

## 3. Build

### 3.1 Prerequisites

- Node ≥ 22, npm ≥ 11
- A Cloudflare account, authenticated:
  ```sh
  npx wrangler login
  ```
- **`--remote` is mandatory for local dev.** Workers AI and Vectorize have no local
  emulation; `wrangler dev` without `--remote` cannot run this.

### 3.2 Create resources — order matters

```sh
# 1. The vector index (384 dims = bge-small-en-v1.5)
npx wrangler vectorize create research-memory --dimensions=384 --metric=cosine

# 2. Metadata index — MUST run before the first insert (see §2.4)
npx wrangler vectorize create-metadata-index research-memory \
  --property-name=type --type=string

# 3. The relational log; paste the returned database_id into wrangler.jsonc
npx wrangler d1 create research-log

# 4. Apply schema
npx wrangler d1 execute research-log --remote --file=./schema.sql
```

### 3.3 Bindings

| Binding | Type | Purpose |
|---|---|---|
| `AI` | Workers AI | Reasoning + embeddings |
| `VECTORIZE` | Vectorize index | Semantic memory, namespaced per run |
| `LOOP` | Workflow | The research loop + self-continuation |
| `DB` | D1 | Runs, source queue, findings, stop flag |

### 3.4 Config vars

| Var | Default | Notes |
|---|---|---|
| `ITERATION_INTERVAL` | `18 minutes` | Pacing. Lower = faster = costs money past the free tier. |
| `REASON_MODEL` | `@cf/meta/llama-3.3-70b-instruct-fp8-fast` | Swap to `@cf/meta/llama-3.1-8b-instruct` for ~2× throughput, lower quality. |
| `EMBED_MODEL` | `@cf/baai/bge-small-en-v1.5` | 384 dims. Must match the index. |
| `ITERATIONS_PER_GEN` | `8` | Bounded by **subrequests, not steps** — a resumed instance accumulates them across iterations in one invocation (bugs.md #1). |
| `MAX_FETCH_BYTES` | `262144` | Ingest size cap (§4.2). |
| `RECALL_TOP_K` | `8` | Chunks recalled per iteration. Raising it raises neuron cost. |
| `FRESH_CHARS` | *(unset → `16000`)* | Characters of the current source carried into the prompt. **Bound by characters, not chunk count** — a count is a newest-N eviction window on a newest-first RSS feed and it silently destroyed a verdict (bugs.md #24). Unset is the normal case; `FRESH_CHARS_DEFAULT` in `workflow.ts` is the one place to change it. |
| `DAILY_NEURON_BUDGET` | `8000` | **Hard spend stop** per UTC day across all runs (§4.4). Deliberately below the 10,000 allocation — see #20. `0` = unlimited. |

### 3.5 Runbook

Live deployment from this build: see `WORKER_URL` in your local `.env` (copy `.env.example`).

**Routes that write or spend need `CONTROL_TOKEN`** — `POST /start`, `/stop`,
`/baseline`, `/step` and `GET /search`, which embeds its query and so bills neurons.
Send it as `authorization: Bearer`; an unset secret denies them all. Reads (`/state`,
`/usage`, `/events`, `GET /baseline`, `/live`) are open, because `liverun.html` polls
them from `file://` and none of them cost anything.

```sh
set -a; . ./.env; set +a
AUTH="authorization: Bearer $CONTROL_TOKEN"

# Start a run
curl -X POST "$WORKER_URL/start" -H "$AUTH" -H 'content-type: application/json' -d '{
  "topic": "Post-quantum cryptography migration in TLS",
  "goals": [
    "Identify which PQC algorithms are standardised and deployed",
    "Find the main performance objections and whether they hold up"
  ],
  "sources": [
    "https://blog.cloudflare.com/pq-2024/",
    "https://datatracker.ietf.org/doc/draft-ietf-tls-hybrid-design/"
  ],
  "maxIterations": 40
}'

# Add "dryRun": true to seed D1 WITHOUT launching the loop — then drive it
# one iteration at a time with POST /step. Use this for any testing.

curl "$WORKER_URL/state?run=<id>"                          # progress + findings
curl -H "$AUTH" "$WORKER_URL/search?run=<id>&q=lattice"    # semantic search — SPENDS
curl -X POST -H "$AUTH" "$WORKER_URL/stop?run=<id>"        # halt at next assess
curl "$WORKER_URL/usage"                                   # neuron spend today vs budget
curl "$WORKER_URL/events?limit=50"                         # the funding-event ledger
curl "$WORKER_URL/baseline"                                # what deltas are measured against

# Set the baseline. Content only — no deploy. Verify by reading it BACK and
# comparing a hash against the file, not by trusting the ok/chars response:
# `chars` is UTF-16 code units and the file is UTF-8 bytes, so the two numbers
# legitimately differ and neither proves the content survived (CLAUDE.md §12).
python -c "import io,json;print(json.dumps({'text':io.open('baseline/AU-AI-FUNDING-2026H1.md',encoding='utf-8').read()}))" > /tmp/bl.json
curl -X POST "$WORKER_URL/baseline" -H "$AUTH" -H 'content-type: application/json' --data-binary @/tmp/bl.json

npx wrangler workflows instances list research-loop
npx wrangler tail
```

#### The daily schedule

Two daily crons (`0 15 * * *` and `0 16 * * *`) run a stored brief once a day.
**Cron Triggers are UTC only — no local time, no DST**, so a fixed expression drifts
an hour against any zone that observes it. Both arms fire every day and `scheduled()`
starts the run only on the one that is 04:00 in `Pacific/Auckland` for the instant
scheduled — 16:00Z under NZST, 15:00Z under NZDT — so the start time holds at 04:00
local across the boundary. Simulating a full year of both arms gives 365 distinct
local days, every one at 04:00: no skipped day at the September transition, no double
run at the April one.

The brief is JSON in D1, so changing topic, goals or seeds needs no deploy:

```sh
# Read the current brief
npx wrangler d1 execute research-log --remote \
  --command "SELECT value FROM control WHERE key='daily_brief'"

# Replace it (topic, goals[], sources[], maxIterations)
npx wrangler d1 execute research-log --remote \
  --command "INSERT OR REPLACE INTO control (key,value) VALUES ('daily_brief','<json>')"

# Force today's run after it has already fired (clears the day-claim)
npx wrangler d1 execute research-log --remote \
  --command "DELETE FROM control WHERE key='daily_last_run'"
```

`DAILY_CRON` in `src/index.ts` **must match the `wrangler.jsonc` string exactly**. A
mismatch does not error — `scheduled()` falls through to the watchdog branch and the
daily run silently never happens.

Test it without deploying or waiting for the clock. `--remote` binds **real secrets
and real resources**, so this exercises the true path:

```sh
npx wrangler dev --remote --test-scheduled --port 8788
curl "http://127.0.0.1:8788/__scheduled?cron=0+16+*+*+*"
```

Watch which handler logs — `[daily]` or `[watchdog]` — to confirm the branch. Restore
any state the test mutated afterwards; a test that leaves `daily_last_run` set will
suppress the real run.

#### Failure alerts

`src/notify.ts` posts to `ALERT_WEBHOOK` on a failed run, a daily run that could not
start, and budget exhaustion. It is a **secret**, never a config var:

```sh
npx wrangler secret put ALERT_WEBHOOK   # Slack or Discord incoming webhook
```

Unset, alerting silently no-ops. The notifier sends `{text}` and `{content}` in one
body so it works with either service, and it never throws — alerting must not fail
the run it is reporting on. Transient platform interruptions are deliberately *not*
alerted: Workflows recovers from those, and paging on them trains you to ignore the
channel.
```

### 4.1 Neuron cost — measured

Text-generation calls return `usage.neurons`, so these are observed values from real
iterations, not arithmetic (embeddings do not — see §2.5 and bugs.md #21):

| Iteration shape | Reason-call neurons |
|---|---|
| First iteration, nothing recalled, 6 fresh excerpts | 28 – 92 |
| Later iteration, 8 recalled + 6 fresh + 6 prior findings | **160** |
| Trivial ping (42 tokens in, 2 out) | 1.5 |

Embeddings are small per call: `bge-small-en-v1.5` is 1,841 neurons/M input tokens,
so ~20 chunks costs well under 10 neurons. **They are not negligible in aggregate,
and this sentence used to say they were** — combined with the unmetered report call
and per-iteration recall embedding, the shortfall reached 21% of a day's allocation
(bugs.md #17). The fix for that then read embeddings as **0** for a further day,
because it assumed a `usage.neurons` field that embeddings do not return (#21).

Every AI call now goes through one `meterCall()`, which takes the provider's figure
where it exists and prices embeddings from `total_tokens` otherwise. **Verified by
reconciliation against Cloudflare's own analytics**, not against itself: reasoning
matched to 14 decimal places and a post-fix embed matched within 0.009%.

**Budget on ~170 neurons/iteration once memory fills up → ~58 iterations/day**
against the free 10,000/day allowance. The original estimate of 126 was optimistic
because it ignored how much the prompt grows once recall and prior findings kick in.

Cost scales with *prompt* size, so the levers that matter are `RECALL_TOP_K` (8),
`FRESH_CHARS` (16,000) and `PRIOR_FINDINGS_IN_PROMPT` (6) — not the model alone.
`FRESH_CHARS` was `FRESH_EXCERPTS = 6` chunks until 2026-08-17; widening it to 16,000
characters costs **+36% reasoning neurons per iteration** (~142 → ~193 measured) and
was worth every one of them — at 6 chunks the loop was reading 7,600 of 13,162
characters of the only seed that carried its answers, and **evicting the evidence for
goal 1 as the feed grew** (bugs.md #24). Note the direction of the tradeoff: this is a
case where the cheaper prompt was quietly producing a worse answer, not a faster one.
Switching to `llama-3.1-8b-instruct` (25,608 in / 75,147 out vs 26,668 / 204,805)
roughly halves output cost at meaningfully lower reasoning quality.

`ITERATION_INTERVAL` of 18 minutes gives ~80 iterations/day, which is slightly
above the free budget at full prompt size. Use 25 minutes to stay comfortably
inside it, or accept overage.

### 4.2 The CPU problem — measured, and it does NOT fit the free plan

Measured via `wrangler tail --format json` on the deployed Worker:

| Page | Fetched | Extracted | Chunks | **cpuTime** | wallTime |
|---|---|---|---|---|---|
| blog.cloudflare.com/cloudflare-computer | 82 KB | 8,699 ch | 7 | **52 ms** | 114 ms |
| developers.cloudflare.com/workflows/rules | 211 KB | 23,875 ch | 20 | **229 ms** | 411 ms |
| blog.cloudflare.com/agents-week-in-review | 73 KB | 12,094 ch | 10 | **33 ms** | 1,926 ms |

**229 ms is 23× the documented 10 ms free-plan CPU limit.** Every request still
returned `outcome: "ok"` rather than being terminated, which indicates the account
running these tests is on **Workers Paid** (30 s default CPU), not Free.

Consequences, stated plainly:

- **On Workers Paid this is a non-issue.** 229 ms against a 30 s budget is 0.8%.
  `MAX_FETCH_BYTES` could be raised well above 256 KB.
- **On a genuinely Free account this ingest path will be killed** on large pages.
  Mitigations that would be required: drop `MAX_FETCH_BYTES` to ~64 KB, restrict
  sources to `text/plain`-friendly endpoints (RSS, JSON APIs, `llms.txt`, `.md`
  mirrors — note the non-HTML path skips parsing entirely), and reduce
  `MAX_TEXT_CHARS`.

**Confirm your plan at dash.cloudflare.com → Workers & Pages → Plans before
relying on either reading.** The CLI does not expose it.

The mitigations already in the ingest path — `HTMLRewriter` rather than regex, the
byte cap, fixed-length slicing, and isolating parse in its own `step.do` — are what
keep 211 KB down to 229 ms rather than seconds. They are worth keeping regardless.

### 4.3 What actually fits in the Free plan, per day

The Free plan is viable **only if you avoid HTML sources.** That single decision
moves ingest from "impossible" to "1 ms". Everything below follows from measurement.

#### Measured CPU by content type

`/step {"probe": url}` against the deployed Worker, CPU read from `wrangler tail`:

| Content type | Source | Bytes | Chunks | **CPU** | vs 10 ms Free limit |
|---|---|---|---|---|---|
| `text/plain` | `vectorize/llms.txt` | 4,346 | 4 | **1 ms** | ✅ 9 ms spare |
| `text/markdown` | `workflows/reference/limits/index.md` | 21,939 | 18 | **1 ms** | ✅ 9 ms spare |
| `text/html` | `example.com` | 399 | 1 | **5 ms** | ✅ 5 ms spare |
| `text/html` | `vectorize/platform/limits/` | 11,769 | 1 | **15 ms** | ❌ 1.5× over |
| `text/html` | `workflows/build/rules-of-workflows/` | 210,681 | 20 | **229–644 ms** | ❌ up to 64× over |

Two things stand out:

1. **Non-HTML costs ~1 ms regardless of size.** A 21 KB markdown file yielding 18
   chunks costs the same 1 ms as a 4 KB text file, because `fetchSource()` skips
   `HTMLRewriter` entirely for non-HTML content types.
2. **HTML has ~4–5 ms of fixed parser overhead** before any content. A 399-byte page
   already costs 5 ms, so even trivial HTML leaves almost no headroom, and a 12 KB
   page is already over budget.

The same 211 KB page measured **229 ms, 594 ms and 644 ms** across runs — CPU varies
by ~3× between invocations, so treat any single measurement as a lower bound.

**Note:** Workflows applies the 10 ms Free limit **per step**, so the ingest step is
capped independently — no borrowing from cheaper steps.

**Confirmed in production, and the failure mode is worse than "does not fit."**
Measured via `wrangler tail --format json`: large HTML pages cost **20–241 ms** and
are killed; a 70 KB page passed at **11 ms**; `/state` and `/usage` cost 1–3 ms. The
enforced ceiling sits between **11 ms and 20 ms**. Yet HTML ingest *appeared* to work
for 40+ iterations across four runs before run `98adcf63` died at iteration 11 — and
`smallbizai` failed at 20 ms here having ingested cleanly minutes earlier. Every
successful HTML ingest was inside **burst allowance, not budget**.
**Intermittent success is not headroom** (bugs.md #15).

#### Per-metric daily budget on Free

Assuming plain-text/markdown sources and ~173 neurons/iteration (160 reason + ~13
embedding, measured):

| Metric | Free limit | Used per iteration | **Iterations/day** |
|---|---|---|---|
| **Workers AI neurons** | 10,000/day | ~173 | **≈ 58** ← binding |
| Worker/Workflow executions | 100,000/day (shared) | ~6 steps | ~16,000 |
| Subrequests | 50/invocation | ~5 | not binding |
| CPU per step | 10 ms | ~1 ms (non-HTML) | not binding |
| D1 queries | 50/invocation | ~3 | not binding |
| D1 storage | 500 MB/db, 5 GB total | ~2 KB | effectively unlimited |
| Vectorize queried dims | 30M/month | 384 | ~2,600/day |
| Vectorize **stored** dims | 5M/month | ~7,700 (20 chunks) | **≈ 650 total, then prune** |
| Workflows concurrent instances | 100 (sleeping instances excluded) | 1 | not binding |
| Workflows steps/instance | 1,024 | 6 | 170/generation |
| Workflows state retention | **3 days** | — | see below |
| Cron triggers | 5/account | 1 | not binding |

**The binding constraint is Workers AI neurons: ~58 iterations/day.**
Everything else has at least an order of magnitude of headroom — except Vectorize
*storage*, which is a cumulative cap rather than a rate: ~650 iterations' worth of
chunks before pruning is required (§4.4).

**Retention interacts with pacing.** A generation must finish inside the 3-day
window, so `ITERATIONS_PER_GEN × ITERATION_INTERVAL < 72 h`. At the current 8 × 18
min = 2.4 h there is ample margin; the constraint only bites if both are raised
together. Keep the product under ~2.5 days.

#### Recommended Free-plan profile

```jsonc
"ITERATION_INTERVAL":  "25 minutes",   // 58 iterations/day, inside the neuron budget
"REASON_MODEL":        "@cf/meta/llama-3.1-8b-instruct",  // ~2x cheaper than 70b
"MAX_SOURCE_DEPTH":    "0",            // seeds only — model-proposed URLs are usually HTML
"DAILY_NEURON_BUDGET": "8000",         // hard stop, below the allocation (bugs.md #20)
```

and **seed only non-HTML sources**:

- `llms.txt` / `llms-full.txt` (most doc sites now publish these)
- `…/index.md` mirrors — Cloudflare's docs serve markdown at any page URL + `/index.md`
- RSS/Atom feeds, JSON APIs, raw.githubusercontent.com, plain `.txt`

With `llama-3.1-8b` instead of `70b`, per-iteration cost drops to roughly 60–80
neurons → **~130–160 iterations/day** on Free.

### 4.4 Billing: what happens past the free quota

| | Free plan | Paid plan ($5/mo minimum) |
|---|---|---|
| Exceed 10,000 neurons/day | Requests **fail with an error** | **Auto-billed** at $0.011 / 1,000 neurons |
| Exceed 100,000 requests/day | Requests **fail with an error** | 10M/mo included, then $0.30/M |
| CPU | Hard 10 ms cap | 30M ms/mo included, then $0.02/M ms |
| **Can you be charged?** | **No. Never.** Hard caps only. | **Yes**, automatically |

**On Free you cannot be billed.** There is no overage path — you get errors, not
invoices. The failure mode is a broken loop, not a bill.

**On Paid, overages are automatic and there is no built-in spend cap.**
[Budget alerts](https://developers.cloudflare.com/billing/manage/budget-alerts/) are
**informational only — they do not pause or cap usage**, and because usage is
processed once daily they fire *the day after* the threshold is crossed. Pay-as-you-go
accounts get an automatic $10 alert, but that is a notification, not a brake.

#### What this loop actually costs on Paid

At ~173 neurons/iteration, past the 10,000/day free allocation:

| Pace | Neurons/day | Billable | Cost/day | Cost/month |
|---|---|---|---|---|
| 58 iterations (free budget) | 10,000 | 0 | **$0.00** | **$0.00** |
| 100 iterations | 17,300 | 7,300 | $0.08 | ~$2.41 |
| 500 iterations | 86,500 | 76,500 | $0.84 | ~$25 |
| Runaway: 1 iteration/min | 249,000 | 239,000 | $2.63 | ~$79 |

A single capped run is cheap — `maxIterations` is clamped to 500, so the worst a
single `/start` can do is ~$0.84. The real risk is *many* runs, or the watchdog
restarting a stalled run repeatedly.

#### Safeguards in this build

Four layers, innermost first:

1. **`DAILY_NEURON_BUDGET` (set to `8000`) — the real hard stop.** Every AI call is
   priced by `meterCall()` the moment it returns and accumulated into the D1 `usage`
   table per UTC day. When the total reaches the budget, the loop terminates with
   `reason='budget-exhausted'`. Set `0` to disable.

   **Why 8000 and not the 10,000 free allocation.** The allocation is *not* enforced
   on a UTC calendar day — a run at 00:05Z on a fresh day, with the meter reading 0,
   was refused; a probe at 00:11Z succeeded (bugs.md #20). The evidence points to a
   rolling ~24 h window, so a calendar-day meter can reset while the platform still
   holds most of a window against the account. The 2,000-neuron margin means the loop
   stops itself — *with a report* — before the platform stops it mid-step.

   Note the metering must happen **per call, on return**, not per step: `step.do`
   re-runs its whole closure on retry and Cloudflare bills every attempt, so a
   step-end total loses the attempts that failed after the call returned (#19).
2. **`/step` is guarded and metered too** — it returns HTTP 429 once the budget is
   spent, and records its own usage. Testing is not a blind spot.
3. **The cron watchdog checks the budget before restarting anything**, so a stalled
   run cannot be resurrected into overspend.
4. **`maxIterations`** (clamped 1–500) and **`POST /stop`** bound each individual run.

```sh
curl https://<worker>/usage      # spend today, budget, 14-day history
```

Verified: with the budget set below current spend, `/step` returned **429** and a
`maxIterations: 10` workflow terminated at **n=1** with `reason=budget-exhausted`.

**Also recommended, outside this codebase:**

- Set a [budget alert](https://developers.cloudflare.com/billing/manage/budget-alerts/)
  at a low dollar figure — it won't stop anything, but it tells you something is wrong.
- Watch the Workers AI dashboard (`https://dash.cloudflare.com/$CF_ACCOUNT_ID/ai/workers-ai`)
  for actual neurons; `/usage` only counts what *this* Worker spent.
- If you want a platform-level dollar cap, route inference through
  [AI Gateway spend limits](https://blog.cloudflare.com/ai-gateway-spend-limits/),
  which hard-block by default. Their applicability to Workers AI (as opposed to
  third-party providers) is not clearly documented — verify before relying on it.
- **Staying on the Free plan is itself the strongest guarantee**: it cannot bill you.

### 4.5 Pruning

At 384 dims and ~8 chunks/iteration, the 5M monthly stored-dimension budget covers
roughly **1,600 iterations/month**. Beyond that, delete completed runs' namespaces
or drop `type:"chunk"` vectors while keeping `type:"finding"` — findings are ~1/8th
the volume and carry most of the value.

### 5.2 Reconciling neuron spend against Cloudflare

**The one check that catches an undercounting meter.** Wrangler's own OAuth token
authenticates the GraphQL analytics API — no dashboard, no separate API token:

```sh
TOK=$(sed -n 's/^oauth_token = "\(.*\)"$/\1/p' "$APPDATA/xdg.config/.wrangler/config/default.toml")
curl -s https://api.cloudflare.com/client/v4/graphql -H "Authorization: Bearer $TOK" \
  -H 'content-type: application/json' \
  --data "{\"query\":\"query{viewer{accounts(filter:{accountTag:\\\"$CF_ACCOUNT_ID\\\"}){aiInferenceAdaptiveGroups(limit:50,filter:{date_geq:\\\"$(date -u +%F)\\\"}){dimensions{date modelId}sum{totalNeurons}count}}}}\"}"
```

Compare against `GET /usage`. `dimensions{modelId}` separates reasoning from
embedding spend — essential, because #21 was a 100% undercount on embeddings alone
while reasoning matched perfectly. `count` gives the true per-model call count, which
is what exposes a meter counting steps instead of calls (#19).

Swap `date` for `datetimeHour` to see the rolling-window behaviour behind #20. Two
caveats: the figures are **account-wide**, so compare deltas across a quiet window
rather than absolute totals; and this dataset is **not** the counter that enforces
the allocation.

### Reproducing check 4 (the one that matters)

If vector memory is broken, everything else still *looks* fine — findings get
written, runs terminate cleanly, and only recall quality silently degrades. This
is the test that catches it:

```sh
W=https://<your-worker>.workers.dev
R=$(curl -s -X POST $W/start -H "$AUTH" -H 'content-type: application/json' -d '{
  "topic":"...","goals":["..."],
  "sources":["<source A>","<source B>"],
  "maxIterations":3,"dryRun":true}' | jq -r .runId)
